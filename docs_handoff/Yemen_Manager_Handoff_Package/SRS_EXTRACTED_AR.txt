Yemen Manager
وثيقة المتطلبات البرمجية والمخطط المعماري وخطة التنفيذ
الإصدار 1.0 — وثيقة تأسيسية قابلة للتنفيذ — 27 أكتوبر 2026
الغرض: توجيه فريق التطوير أو نموذج ذكاء اصطناعي لبناء تطبيق أندرويد محليّ التشغيل، غني بالأدوات، مع الحفاظ على الرشاقة والبساطة والموثوقية.
حالة الوثيقة: أساس معتمد للتخطيط. أي قرار تنفيذي غير محسوم يجب تسجيله في سجل القرارات، وعدم اختراع واجهات برمجية أو ادعاء اكتمال ميزة لم تُختبر.
1. الملخص التنفيذي
Yemen Manager تطبيق أندرويد لإدارة الملفات وتحليل حزم التطبيقات وتحرير النصوص والموارد والبيانات الثنائية، مع مساحة عمل للمطورين ومحركات إضافية اختيارية. المنتج محلي أولًا وبلا اعتماد على خوادم أو حسابات أو اتصال إنترنت. يمكن لاحقًا استخدام الشبكة المحلية أو بروتوكولات التخزين البعيد عند تفعيلها يدويًا؛ وجود هذه الوظائف لا يعني أنها تحتاج إلى الإنترنت العام.
الهدف ليس وضع كل أداة على الشاشة الرئيسية، بل توفير قدرات واسعة من خلال واجهة سياقية: تظهر الأدوات المناسبة لنوع الملف، بينما تبقى الأدوات المتقدمة في مساحة مستقلة.
قاعدة غير قابلة للتفاوض: لا تُعرض أي ميزة على أنها جاهزة ما لم تكن منفذة فعليًا ومختبرة. إذا تعذر تنفيذ ميزة، تُوثق حدودها ويُقدم بديل واضح بدلًا من زر شكلي أو محاكاة مضللة.
2. الرؤية والمنتج
الاسم: Yemen Manager. الاسم التجاري والشعار النهائيان يخضعان لمراجعة لاحقة؛ لا تُقلّد شعارات أو أصولًا بصرية خاصة بتطبيق آخر.
الشعار الوصفي المقترح: Advanced Android File & App Toolkit.
المبادئ: محلي افتراضيًا؛ سريع دون وعود أداء غير مقاسة؛ واجهة هادئة؛ عمليات قابلة للتتبع؛ حماية الملف الأصلي؛ وحدات مستقلة؛ دعم العربية والإنجليزية؛ توافق واضح مع قيود أندرويد.

3. النطاق والحدود
3.1 داخل النطاق
مدير ملفات ثنائي اللوحة، تبويبات، مفضلة، سجل مسارات، تحديد متعدد، نسخ ونقل وإعادة تسمية وحذف وإنشاء مجلدات.
البحث والفرز والمرشحات والخصائص والبصمات الرقمية ومعاينة النصوص والصور والملفات المدعومة.
أرشفة ZIP وصيغ إضافية وفق المكتبات المرخصة والمدمجة، مع معالجة متدفقة حيثما أمكن.
محرر نصوص ومحرر Hex ومقارنة الملفات وسجل محلي للتغييرات.
تحليل APK وManifest وموارد XML وDEX وملفات JAR وClass، وفق حدود المكتبات والتنسيقات.
تحرير موارد محددة وإعادة بناء APK والتحقق منه وتوقيعه بمفتاح يملكه المستخدم، عندما تدعم الأدوات العملية.
عرض التطبيقات المثبتة واستخراج APK أو split APKs حيث تسمح واجهات النظام.
تكامل اختياري مع SAF وShizuku وRoot، وكل مزود صلاحيات مستقل وقابل للفشل بأمان.
FTP/FTPS/SFTP/SMB/WebDAV ووسائط USB/SD كوظائف اختيارية، مع توثيق التوافق والأمان. بروتوكولات الشبكة المحلية يمكنها العمل دون إنترنت عام.
نظام إضافات محدود الصلاحيات وسكربتات آمنة، بعد تأسيس واجهات ثابتة واختبارات أمان.
3.2 خارج النطاق أو مشروط بالمراجعة
لا يُفترض وجود وصول مضمون إلى Android/data أو Android/obb؛ يخضع ذلك لإصدار أندرويد وواجهات النظام والصلاحيات.
لا يُفترض أن Shizuku أو Dhizuku يمنحان كل الصلاحيات أو يضمنان التثبيت الصامت.
لا يوجد ضمان عام لاستعادة أسماء التعتيم الأصلية أو إصلاح كل DEX تالف أو استرجاع المصدر الأصلي من bytecode.
لا تُنفذ تلقائيًا أدوات تجاوز فحوص التوقيع أو تعطيل حماية تطبيقات الغير. يُسمح بالتحليل والتوقيع المشروع واختبار التطبيقات التي يملك المستخدم صلاحية اختبارها.
لا تُدمج خزانة كلمات مرور أو مفاتيح دون تصميم تخزين آمن واختبارات؛ لا تُكتب الأسرار في السجلات أو النسخ الاحتياطية غير المشفرة.
لا تُنفذ اعتراضات HTTPS أو تجاوز SSL pinning بصورة عامة أو خفية. أي مختبر ديناميكي يجب أن يكون اختياريًا، واضح النطاق، ومخصصًا للاختبار المصرح به.
4. الجمهور وسيناريوهات الاستخدام
مستخدم متقدم يريد إدارة ملفات الهاتف والأرشيفات بسرعة.
مطوّر أندرويد يريد فحص APK وManifest والموارد والتوقيع.
باحث أو مختبر أمني مخوّل يريد تحليل حزمة في وضع ساكن وإنتاج تقرير.
مترجم يريد استخراج السلاسل النصية ومراجعة موارد اللغات.
مستخدم لديه صلاحيات متقدمة ويريد تنفيذ عمليات محددة مع توضيح الصلاحيات المطلوبة.
5. المعمارية العامة
البنية المقترحة: تطبيق Android أصلي باستخدام Kotlin وJetpack Compose، مع محركات JVM متخصصة للتنسيقات التي لها مكتبات ناضجة، واستخدام Rust عبر JNI فقط للعمليات التي تثبت القياسات أنه يحسن الأداء أو السلامة. لا تُكتب كل المحركات بلغة واحدة لمجرد التوحيد.

6. التقنية المقترحة وسياسة الاعتماديات
Kotlin وJetpack Compose وMaterial 3 مع design tokens خاصة بالتطبيق.
Coroutines وFlow للعمليات غير المتزامنة وتحديث حالة الواجهة.
ViewModel لإدارة حالة الشاشة، مع فصل حالات العرض عن منطق الأعمال.
Room أو تخزين محلي مناسب للإعدادات وسجل العمليات، بعد تقدير حجم البيانات.
JADX للعرض التقريبي لكود Java، مع احترام الترخيص ومتطلبات التوزيع والتبعيات. لا يُفترض أنه محرر يعيد المصدر الأصلي.
smali/baksmali أو dexlib2 لتحليل DEX وSmali بعد مراجعة الترخيص والتوافق.
apktool أو مكتبات ملائمة لـ AXML/ARSC بعد تدقيق الترخيص وقيود الاستخدام وإمكانية دمجها offline.
Rust عبر JNI لمحركات منتقاة فقط، مع حدود ذاكرة واضحة واختبارات fuzzing للتعامل مع المدخلات غير الموثوقة.
كل dependency يجب أن يكون له: اسم وإصدار ثابت، ترخيص، مصدر موثوق، hash، متطلبات SDK، حجم تقريبي، حالة صيانة، ومبرر إدراجه.
شرط عدم وجود إنترنت أثناء التطوير: يجب تجهيز بيئة بناء offline مسبقًا، بما فيها Android SDK وJDK وGradle wrapper والتبعيات المخزنة محليًا وملفات Rust crates المطلوبة. لا يمكن تنزيل تبعيات جديدة أثناء العمل بلا اتصال؛ لذلك لا يبدأ البناء قبل التحقق من اكتمال المخزون المحلي.
7. المتطلبات الوظيفية
7.1 مدير الملفات
FR-FM-001: عرض لوحتين مستقلتين، لكل لوحة URI/مسار حالي وسجل تنقل مستقل.
FR-FM-002: نسخ/نقل/إعادة تسمية/حذف/إنشاء، مع نتيجة صريحة لكل عملية ومعالجة الأخطاء الجزئية.
FR-FM-003: تحديد متعدد وعمليات جماعية مع معاينة موجزة لما سيحدث قبل العمليات المدمرة.
FR-FM-004: دعم مزودات SAF وعدم افتراض صلاحيات عامة للتخزين.
FR-FM-005: البحث بالاسم والامتداد والحجم والتاريخ، مع إمكانية إيقاف البحث.
FR-FM-006: عرض خصائص الملف، MIME/type، الحجم، التواريخ المتاحة والبصمات عند الطلب.
FR-FM-007: سلة محذوفات اختيارية داخل مساحة يستطيع التطبيق إدارتها؛ توضيح أن بعض المزودات لا تسمح بنقل ذري أو استرجاع مضمون.
FR-FM-008: نقل متدفق للملفات الكبيرة مع إظهار التقدم وإلغاء آمن حيث يمكن.
FR-FM-009: لا يُحذف المصدر بعد النسخ أو التحويل إلا بطلب صريح منفصل.
FR-FM-010: دعم التبويبات والمفضلة والمسارات الأخيرة مع خيار مسح السجل.
7.2 الأرشيفات
FR-AR-001: استعراض محتويات الأرشيف قبل الاستخراج.
FR-AR-002: استخراج انتقائي أو كامل إلى وجهة يختارها المستخدم.
FR-AR-003: إنشاء أرشيف وإضافة/استبدال مدخلات وفق ما يدعمه المحرك.
FR-AR-004: معالجة streaming حيثما أمكن، وعدم تحميل الأرشيف كله إلى الذاكرة دون حاجة.
FR-AR-005: الحماية من Zip Slip ومسارات الخروج من مجلد الوجهة، ومن أحجام التوسع غير المعقولة، ومن الأرشيفات المتداخلة الخبيثة.
FR-AR-006: عرض تنبيه عند أرشيف مشفر أو تنسيق غير مدعوم؛ لا تُعرض نجاحات وهمية.
7.3 محررات النص وHex والمقارنة
FR-ED-001: محرر نصوص بترميز محدد بوضوح، وتلوين صيغ متفق عليها، وأرقام أسطر، وبحث واستبدال، وRegex اختياري.
FR-ED-002: سجل undo/redo محدود بالذاكرة أو القرص وفق إعدادات واضحة، مع عدم ادعاء «لا نهائي» دون حدود عملية.
FR-ED-003: محرر Hex يعرض offset والبايتات وتمثيل ASCII، ويتيح البحث وتعديل نطاقات محددة.
FR-ED-004: لا يُحفظ التعديل فوق الأصل مباشرة افتراضيًا؛ تُستخدم نسخة عمل أو كتابة ذرية عند دعم مزود التخزين.
FR-ED-005: مقارنة نصية وثنائية، مع بيان حدود المقارنة عند الملفات الكبيرة.
FR-ED-006: حفظ دوري اختياري للمسودات محليًا مع حماية بيانات المستخدم وإتاحة استعادتها.
7.4 APK وManifest وموارد Android
FR-APK-001: فحص نوع الحزمة وبنيتها قبل التحليل.
FR-APK-002: عرض أسماء المدخلات وأحجامها وبياناتها الأساسية دون تنفيذ أي محتوى.
FR-APK-003: تحليل Manifest وإظهار package/applicationId عند توفره، SDK، الأذونات المعلنة، والمكونات.
FR-APK-004: التمييز بين الأذونات المعلنة والأذونات الممنوحة فعليًا.
FR-APK-005: عرض الموارد وملفات DEX والأصول والتوقيع ضمن تبويبات متخصصة.
FR-APK-006: تحرير Manifest أو موارد محددة عبر نموذج بيانات، لا عبر استبدال نصي أعمى في الملفات الثنائية.
FR-APK-007: قبل إعادة البناء، إظهار ملخص التغييرات والتحذيرات والقيود.
FR-APK-008: بعد البناء، التحقق من سلامة الأرشيف وإمكان قراءة Manifest والموارد التي يدعمها المحرك.
FR-APK-009: عند تعديل APK، توضيح أن التوقيع الأصلي لا يبقى صالحًا عادةً، وعرض خيارات توقيع بمفتاح يملكه المستخدم.
FR-APK-010: عدم ادعاء نجاح التثبيت أو التوافق دون نتيجة موثقة من النظام.
7.5 DEX وSmali وDecompiler
FR-DEX-001: عرض ملفات classes.dex المتعددة مع إظهار أخطاء التحليل.
FR-DEX-002: فهرسة الحزم والفئات والدوال والحقول والسلاسل حيث يسمح المحرك.
FR-DEX-003: عرض Smali للقراءة والتحرير ضمن نطاق دعم المكتبة.
FR-DEX-004: Java decompilation بوصفه عرضًا تقديريًا؛ ربطه بملف/فئة المصدر المعروفة عند الإمكان.
FR-DEX-005: البحث في النصوص والفئات والتواقيع مع إمكان إلغاء الفهرسة.
FR-DEX-006: أي إعادة تقسيم DEX يجب أن تتحقق من مراجع الأنواع والدوال وحدود التنسيق ثم تعيد بناء الحزمة واختبارها.
FR-DEX-007: ميزات de-obfuscation تميز بين الأسماء المؤكدة والاقتراحات، ولا تعد باستعادة المصدر الأصلي.
FR-DEX-008: فك تشفير النصوص ليس عامًا؛ أي محلل مخصص يقدمه المستخدم يعمل في وضع آمن، مع توضيح أنه لا يمكن ضمان اكتشاف جميع طرق التشفير.
FR-DEX-009: الإصلاحات البنيوية تحفظ نسخة أصلية وتعرض تقريرًا قبل كتابة المخرجات.
7.6 التطبيقات المثبتة والتثبيت
FR-PKG-001: فصل التطبيقات التي يراها النظام كتطبيقات مستخدم وتطبيقات نظام، مع توضيح حدود الرؤية بحسب إصدار Android.
FR-PKG-002: عرض بيانات الحزمة التي يمكن للنظام توفيرها، دون اختلاق UID أو تواريخ أو معلومات توقيع غير متاحة.
FR-PKG-003: استخراج base APK وsplit APKs بصورة منفصلة، وعدم دمج split packages في APK واحد إلا إذا كانت هناك طريقة صحيحة ومدعومة؛ الأصل أن الحزمة المقسمة تُثبت كمجموعة متوافقة.
FR-PKG-004: التحقق من اختلاف التوقيع أو خفض versionCode قبل محاولة التثبيت متى توفرت البيانات.

FR-NET-006: لا تُرسل بيانات أو سجلات إلى خدمات خارجية.

10. إدارة الصلاحيات والأمان
اعتماد أقل صلاحية لازمة لكل عملية.
شرح سبب طلب كل صلاحية في السياق قبل الانتقال إلى إعدادات النظام.
لا توجد عملية root مخفية أو أوامر shell غير معروضة للمستخدم عند كونها مؤثرة.
عرض الأمر أو الأثر قبل تنفيذ العمليات الحساسة، مع تأكيد إضافي للكتابة أو الحذف الجماعي.
التعامل مع APK وZIP وDEX وXML كمدخلات غير موثوقة؛ استخدام حدود للحجم والعمق والوقت.
حماية من Zip Slip وpath traversal وملفات التوسع الضخمة وinteger overflow وparser crashes.
حفظ آمن: كتابة إلى ملف مؤقت ثم التحقق ثم الاستبدال عند دعم مزود التخزين؛ خلاف ذلك إظهار أن العملية ليست ذرية.
لا تُسجّل كلمات المرور أو المفاتيح أو محتوى الملفات أو بيانات الشبكة الحساسة.
أي تحليل ديناميكي أو اتصال شبكي يتطلب اختيارًا صريحًا من المستخدم ونطاقًا واضحًا.

14. نموذج البيانات وعقود العمليات
كل عملية طويلة تستخدم نموذجًا موحدًا على الأقل: OperationId، OperationType، SourceReferences، DestinationReference، Status، Progress (اختياري)، StartedAt، FinishedAt، Warnings، ErrorCode، ErrorMessage، OutputReferences، Recoverability.
حالات العملية المقترحة: QUEUED، RUNNING، CANCELLING، SUCCEEDED، SUCCEEDED_WITH_WARNINGS، FAILED، CANCELLED. لا تُحوّل عملية فاشلة جزئيًا إلى SUCCEEDED.
أخطاء المجال تكون typed، مثل PermissionDenied، UnsupportedFormat، CorruptInput، DestinationExists، InsufficientSpace، Cancelled، ValidationFailed، EngineUnavailable. لا تعرض للمستخدم stack trace خامًا؛ يُحفظ تشخيص منقح اختياريًا.
واجهات التخزين يجب أن تدعم: openRead، openWrite أو كتابة مؤقتة إذا أمكن، list، metadata، delete، rename/move عند الدعم، capability query. لا تفترض أن كل مزود يدعم rename أو seek أو atomic write.
15. إدارة الأداء والذاكرة
استخدم streaming للنسخ والاستخراج والهاش عندما يسمح المحرك.
لا تُنشئ byte array كاملة لملف كبير دون حد واضح ومبرر.
استخدم pagination أو lazy lists للمجلدات الطويلة.
افصل العمل الثقيل عن Main thread، مع إلغاء تعاوني.
حدد حدودًا للذاكرة المؤقتة والفهارس، وأتح للمستخدم مسحها.
ضع benchmarks ثابتة بملفات اختبار معلومة الحجم والنتيجة.
لا تستخدم Rust إلا إذا كان هناك مكسب مقاس أو حاجة إلى تحكم منخفض المستوى.
16. قرارات يجب تسجيلها قبل البرمجة
أقل إصدار Android مستهدف وtargetSdk وفق متطلبات التوزيع والمكتبات.
هل سيُوزع التطبيق خارج متجر رسمي؟ يؤثر ذلك في آلية التثبيت والتحديث والتوقيع.
الترخيص المقبول لكل dependency، وطريقة تضمين notices.
صيغ الأرشيف المطلوبة في الإصدار الأول.
حدود حجم الملفات والذاكرة للأجهزة المستهدفة.
هل نظام الإضافات مؤجل حتى الإصدار الثاني؟ التوصية: نعم.
هل توجد بيئة بناء offline جاهزة؟ إن لم توجد، يلزم تجهيزها قبل تنفيذ المهام التي تحتاج تبعيات خارجية.
مصدر ملفات الاختبار وحقوق استخدامها.

18. تعريف الإنجاز النهائي
يُعد Yemen Manager جاهزًا لإصدار أولي عندما تُنجز الوظائف المعتمدة في نطاق الإصدار، وتنجح الاختبارات الأساسية، وتعمل الوظائف المحلية دون اتصال إنترنت، وتُعرض القيود بوضوح، ولا توجد أعطال حرجة معروفة أو مخاطر فقدان بيانات غير معالجة. وجود قائمة أدوات أو واجهات مرسومة وحده لا يعني اكتمال المنتج.
يجب أن يصاحب كل إصدار: سجل تغييرات، قائمة ميزات مكتملة/تجريبية/مؤجلة، قائمة التبعيات وتراخيصها، تعليمات بناء offline، ونتائج الاختبارات.
19. التوجيه الرئيسي للنموذج البرمجي (Master Prompt)
انسخ النص التالي إلى نموذج البرمجة الذي سيعمل على المستودع. هذا التوجيه مصمم للعمل التكراري؛ لا تطلب منه توليد المشروع كاملًا في رد واحد.
أنت تعمل كمهندس برمجيات أندرويد رئيسي ومهندس معماري ومراجع جودة لمشروع Yemen Manager. مهمتك بناء تطبيق حقيقي قابل للبناء والاختبار، لا نموذج واجهات وهمي.
 
المرجعية:
- اتبع وثيقة Yemen Manager SRS & Architecture Blueprint المرفقة بوصفها المرجع الأعلى للمتطلبات.
- اسم التطبيق الظاهر: Yemen Manager.
- المنتج محلي أولًا: لا تسجيل دخول، لا تحليلات سحابية، لا اتصالات تلقائية، ولا اعتماد على خادم خارجي للوظائف الأساسية.
- البروتوكولات المحلية/الشبكية اختيارية ولا تعني اتصالًا بالإنترنت العام.
- التقنية المبدئية: Kotlin + Jetpack Compose؛ استخدم Rust/JNI فقط لوحدة لها مبرر أداء أو معالجة ثنائية مثبت، وليس لمجرد استخدام Rust.
- لا تقلّد العلامة التجارية أو الأصول البصرية لتطبيق آخر.
- لا تدّع تنفيذ ميزة لم تُكتب وتُختبر فعليًا.
 
قواعد تنفيذ إلزامية:
1. ابدأ بفحص المستودع والبيئة والملفات المتاحة، ثم لخّص الحالة الفعلية قبل التعديل.
2. تحقق من توفر JDK وAndroid SDK وGradle والتبعيات محليًا. بما أن البيئة قد تكون دون إنترنت، لا تعتمد على تنزيلات وقت البناء. إذا كان اعتماد مفقودًا، أوقف الجزء الذي يحتاجه وسجّل الاسم والإصدار والسبب، ولا تخترع نسخة بديلة.
3. نفّذ على مراحل صغيرة قابلة للبناء. لا تنشئ مئات الملفات دفعة واحدة ولا تستبدل ملفات غير مرتبطة بالمهمة.
4. قبل كل مرحلة، اذكر الهدف والملفات التي ستنشئها أو تعدلها ومعايير قبولها. بعد التنفيذ، شغّل الاختبارات أو البناء المتاح، واعرض النتائج الفعلية.
5. استخدم بنية طبقية: UI، domain/use cases، storage providers، engines، privilege providers. امنع اعتماد محركات الملفات على Compose.
6. كل عملية طويلة يجب أن تكون غير حاجبة للواجهة، ذات حالة وتقدم عند إمكان القياس، وإلغاء تعاوني عند الدعم، وأخطاء typed.
7. لا تفترض أن URI هو مسار ملف. استخدم SAF ومزودات التخزين وفق قدراتها الفعلية.
8. لا تحمّل ملفًا كبيرًا كاملًا في الذاكرة دون ضرورة وحدود موثقة. فضّل streaming وكتابة آمنة.
9. لا تعدّل الأصل مباشرة افتراضيًا. أنشئ نسخة عمل أو ملفًا مؤقتًا، تحقق من الناتج، ثم استبدل الأصل فقط إذا كان ذلك مدعومًا وآمنًا ومطلوبًا صراحة.
10. تعامل مع APK وZIP وDEX وXML كمدخلات غير موثوقة. لا تنفّذ محتوياتها. تحقّق من الحدود والمسارات والأحجام والأخطاء.
11. لا تُنفّذ تجاوز حماية التوقيع أو تعطيل ضوابط أمان تطبيقات الغير. ادعم التحليل والتعديل والتوقيع المشروع للتطبيقات التي يملك المستخدم حق تعديلها أو اختبارها.
12. Shizuku وRoot وأي تكامل Device Owner اختياري. افحص الصلاحيات والقدرات في وقت التشغيل، ولا تفترض نجاحًا مضمونًا أو تثبيتًا صامتًا.
13. لا تدّع استعادة أسماء obfuscation الأصلية أو إصلاح كل ملف تالف أو دمج split APKs في APK واحد بصورة عامة.
14. كل dependency يحتاج إصدارًا ثابتًا، وترخيصًا، ومبررًا، وتوافقًا مع offline build. لا تضف مكتبة قبل فحص هذه الأمور.
15. دعم العربية RTL والإنجليزية LTR جزء من التصميم الأساسي، وليس تحسينًا لاحقًا.
16. لا تضع أسرارًا أو كلمات مرور أو محتوى حساسًا في السجلات. لا تستخدم اتصالات شبكة مخفية.
17. عند عدم اليقين، لا تختلق API أو نتيجة اختبار. صرّح بما لم يمكن التحقق منه وقدّم أصغر خطوة تالية قابلة للتحقق.
18. حافظ على README، وسجل القرارات التقنية ADR، وقائمة التبعيات، وخطة الاختبار، وسجل التغييرات.
 
دورة العمل لكل مهمة:
أ) افهم المتطلب واربطه بمعرف FR/NFR من الوثيقة.
ب) حدّد السلوك المطلوب وحالات النجاح والفشل والإلغاء والصلاحيات.
ج) حدّد الملفات والعقود المتأثرة، وتحقق من عدم كسر حدود الوحدات.
د) نفّذ أصغر تغيير مكتمل.
هـ) أضف اختبارات مناسبة، بما فيها حالات الحدود والفشل.
و) شغّل الاختبارات والبناء المتاحين؛ لا تذكر نجاحًا إلا إذا أظهرته الأداة فعليًا.
ز) راجع الأمان والأداء وRTL وإمكانية الوصول.
ح) لخّص الملفات المعدلة، والأوامر المنفذة، والنتائج، والقيود، والخطوة التالية.
 
أول مهمة فقط:
1. افحص المستودع والبيئة دون تعديل ملفات.
2. اكتشف بنية المشروع والتبعيات المتاحة ونسخ JDK/Gradle/SDK إن أمكن.
3. أعد تقريرًا مختصرًا عن الجاهزية للعمل دون إنترنت، والمعلومات الناقصة، والمخاطر.
4. اقترح خطة أول مرحلة P0/P1 وملفاتها ومعايير قبولها.
5. لا تبدأ إنشاء الشيفرة قبل عرض تقرير الفحص والخطة، إلا إذا طلب المستخدم صراحة بدء التنفيذ بعد التقرير.
 
مخرجاتك يجب أن تكون عملية ودقيقة. لا تستخدم عبارات مثل «تم التنفيذ بالكامل» إلا مع دليل. لا تنتقل إلى ميزة جديدة إذا فشل البناء أو اختبار حرج في الميزة الحالية.
20. أول أمر تنفيذي مقترح
بعد إرفاق الوثيقة إلى بيئة التطوير، أرسل للنموذج: «ابدأ بالمهمة الأولى المحددة في Master Prompt فقط. افحص بيئة العمل والمستودع دون تعديل ملفات، ثم أخرج تقرير الجاهزية وخطة P0/P1 ومعايير القبول. لا تكتب الكود قبل التقرير».
إذا كانت بيئة التطوير لا تملك وصولًا إلى المستودع أو أدوات تشغيل البناء، فعلى النموذج التصريح بذلك بدلًا من ادعاء الفحص.
